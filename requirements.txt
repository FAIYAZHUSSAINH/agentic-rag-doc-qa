# NOTE ON THIS FILE (Phase 1 fix):
# The original requirements.txt was a raw `pip freeze` of someone's dev
# environment - 200+ packages, including torch, fastai, spacy, unstructured,
# and openai, none of which any .py file in this repo actually imports
# (verified with a grep across all `import`/`from` lines). A frozen
# environment like that is a portfolio-project red flag: it usually means
# "it worked on my machine and I never audited why." It also nearly
# guarantees install failures on a different OS/Python version, since exact
# pins (e.g. onnxruntime==1.19.2) may not have wheels for your interpreter.
#
# This file lists only what's actually imported, with loose (">=") version
# floors instead of hard pins, so pip can resolve versions that have wheels
# for whatever Python you're running, rather than failing on an exact old
# pin. The tradeoff: builds are less byte-for-byte reproducible than a fully
# pinned freeze. For a portfolio project, "it installs reliably" beats
# "it's bit-for-bit reproducible" - if you needed the latter (e.g. shipping
# to prod), you'd pin exact versions with `pip freeze` AFTER confirming this
# set works, or use a lockfile tool like pip-tools/uv.
# -----------------------------------------------------------------------

# chromadb needs SQLite >= 3.35. Some Linux base images (e.g. Debian slim,
# which we'll use for the Docker image in Phase 4) ship an older system
# sqlite3 than that. pysqlite3-binary bundles a modern SQLite as a drop-in
# replacement for those environments. It ships no Windows wheels at all, so
# it's gated to Linux here - on Windows/macOS dev machines the interpreter's
# built-in sqlite3 is already new enough, and the code (see the try/except
# around the pysqlite3 shim in rag_api.py/create_db.py/query.py) skips the
# swap gracefully when the package isn't installed.
pysqlite3-binary; sys_platform == "linux"
